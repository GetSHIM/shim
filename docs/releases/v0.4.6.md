# shim v0.4.6

A patch release on v0.4.5. The enterprise and cloud gateways and their workers get
the startup-hook and egress guards that `shim serve` got in v0.4.5. Both guards report
by default, and the enterprise CI image smoke runs them in `enforce`. A model
deployment's health check retries once after a network error. No migrations and no
new settings. In the community gateway, one more metadata address is refused.

## Process guards in the enterprise and cloud images

- **Gateway.** The enterprise and cloud images start
  `uvicorn shim_enterprise.guards:guarded_app --factory` and
  `uvicorn shim_cloud.guards:guarded_app --factory`. Both install the guards before
  the application is imported, then build it as before. A deployment that overrides
  the image command with `create_enterprise_app` or `create_cloud_app` runs without
  guards.
- **Workers.** `python -m shim_enterprise.workers.{outbox,reconciliation,compliance,ai_act}`
  and `python -m shim_cloud.worker` install the guards before their loop. The
  outbox, compliance and cloud workers deliver to tenants' own public hosts, so they
  check only metadata and link-local addresses. `python -m shim_cloud.migrate` runs the
  startup scan only.
- **Allowlist.** The egress guard also allows the hosts the enterprise settings
  name: the database, Redis, Supabase, the OIDC issuer and its discovered token,
  JWKS and userinfo endpoints, Vault or Key Vault, the deployment and alert origins,
  the AWS URL templates, the Entra authority, OpenAI's compliance API, and Resend.
  Instance metadata is allowed only for a secret backend or AWS identity that reads
  credentials from it, or with the WORM archive on. The list is in
  [supply chain](../SUPPLY_CHAIN.md#process-guards).
- EKS Pod Identity's `169.254.170.23` and `fd00:ec2::23` count as metadata in every
  edition, `shim serve` included. The first was already refused as a link-local
  address and is now counted as `kind="metadata"`; the second, a unique local IPv6
  address, was allowed and is now refused.
- GCP Secret Manager's client speaks gRPC from native code, so the guard does not
  see its traffic; the token it sends is fetched in Python and is checked.

## Model deployments

- The deployment health check retries once after a network error or timeout, and
  logs why a check failed: the status, or the error type, never the URL or the
  credential.

## Upgrading

- **Logs.** An install that works today keeps working. It can gain WARNING lines,
  `startup_hook_unexpected` and `egress_denied`, as `shim serve` did in v0.4.5.
- **Before `enforce`.** Run in `report` and read the `egress_denied` lines. List any
  proxy, and the webhook hosts tenants may save as forward targets, in
  `SHIM_EGRESS_ALLOW_HOSTS`: under `enforce` the gateway refuses an unlisted target
  with 422 when it is saved. Tenants' deployments need no entry: their base URLs
  already match the deployment origin lists.
- **Your own command.** If your deployment starts the gateway with its own
  command, switch it to `shim_enterprise.guards:guarded_app` (or
  `shim_cloud.guards:guarded_app`) to get the guards.

## Not in this release

- A guard for processes started with `subprocess` or `os.exec*`, including the
  Alembic child of `shim_cloud.migrate` and migrations run with `alembic` directly.
- Native traffic, such as gRPC.
- `enforce` as the default.

## Rolling back

No migrations. Roll back by moving traffic to the v0.4.5 revision, or set both
guards to `off`.
